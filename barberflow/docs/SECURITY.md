# Безопасность

> Документ описывает технические меры MVP. Юридическое соответствие законодательству Республики
> Узбекистан о персональных данных (в т.ч. требования к локализации и согласиям) **не заявляется**
> и требует отдельной проверки юристом.

## Модель доверия

В продукте нет Telegram-бота и SMS, поэтому **телефоны не подтверждаются**. Отсюда правила:

- Номер телефона сам по себе не даёт никаких прав. Роль PLATFORM_ADMIN выдаётся только командой
  `pnpm admin:create` (доступ к серверу/БД), а в команду бизнеса попадают только по секретной ссылке-приглашению.
- Клиент не входит в систему. Его права на конкретную запись подтверждает секретная ссылка `/a/<token>`,
  которую он получает сразу после записи.
- Кто-то может зарегистрироваться на чужой номер раньше владельца номера (подтвердить номер нечем). Это не даёт
  доступа ни к одному бизнесу. Спорные случаи решает администратор платформы.

## Реализовано

| Мера | Как |
| --- | --- |
| Изоляция арендаторов | `BusinessAccessGuard` проверяет активное членство по `:businessId`; каждый запрос дополнительно фильтруется по `businessId`. Тесты: владелец A получает 403 на 6 маршрутах бизнеса B и 404 при подстановке ID из B в свой бизнес |
| RBAC | `OWNER`, `MANAGER`, `BARBER` (через membership), `PLATFORM_ADMIN`. Барбер управляет только своим графиком/записями. Клиентов видит только тех, у кого есть его неотменённая запись, и в их карточке — только свои визиты; выбрать чужую карточку по ID или узнать её через «создать клиента» по телефону нельзя (`CUSTOMER_EXISTS`). Проверки — на сервере; UI лишь скрывает недоступные разделы |
| Пароли сотрудников | scrypt (N=16384, r=8, p=1, соль 16 байт), параметры хранятся вместе с хешем. Сравнение за постоянное время; для несуществующего номера выполняется та же работа. Одинаковый ответ на «нет такого номера» и «неверный пароль». Минимум 8 символов |
| Подбор пароля | 10 попыток входа / 10 мин с IP; после 5 неудач подряд аккаунт блокируется на 15 минут (`ACCOUNT_LOCKED`), событие пишется в аудит |
| Восстановление без SMS | Владелец выдаёт временный пароль только сотруднику, чей аккаунт целиком внутри его бизнеса: активный не-владелец, без членства в других бизнесах и без роли платформы (`RESET_NOT_ALLOWED`). Остальных сбрасывает администратор платформы. Временный пароль показывается один раз, все сессии отзываются, и сервер (`AuthGuard`) до смены пароля пропускает только `/auth/me`, `/auth/password`, `/auth/logout` (`PASSWORD_CHANGE_REQUIRED`) |
| Смена пароля | Требует текущий пароль; завершает сессии на других устройствах |
| Сессии | 32 случайных байта в HttpOnly, SameSite=Lax cookie (Secure в production); в БД — sha256. Отзыв при выходе, смене/сбросе пароля, удалении аккаунта. Worker удаляет истёкшие сессии |
| Секретные ссылки | Запись клиента и приглашение — 32 случайных байта (base64url), в БД только sha256; формат проверяется до запроса к БД; `noindex` и `Referrer-Policy: no-referrer` на страницах `/a/*` и `/invite/*`. Приглашения одноразовые и истекают через 14 дней. Повтор гостевого запроса с тем же `Idempotency-Key` выдаёт новый токен, старый перестаёт работать |
| Спам гостевыми записями | 10 записей / 10 мин с IP; не больше 3 будущих активных записей на один номер в бизнесе (`TOO_MANY_BOOKINGS`); владелец видит источник записи, отмечает неявки и может обезличить клиента |
| CSRF | SameSite=Lax + отклонение POST/PUT/PATCH/DELETE с чужим `Origin` |
| Валидация | Zod-схемы на каждый body/query; телефоны нормализуются в E.164 (+998); UUID-параметры проверяются |
| Rate limiting | `@nestjs/throttler`: 300/мин глобально, строже на вход, регистрацию, запись, ссылки и приглашения. `RELAX_RATE_LIMITS` (dev/E2E) запрещён в production — API не стартует |
| Перебор ID | UUID v4 для всех сущностей; одинаковый ответ для «нет доступа» и «не существует» на уровне бизнеса |
| Аудит | `audit_logs`: регистрация, вход, блокировка, смена и сброс паролей, создание/изменение бизнеса, услуг (с ценой до/после), мастеров, графика, команды, приглашения, экспорт/обезличивание клиента, блокировки бизнесов, платежи, тарифы, создание администратора через CLI |
| Ошибки | Клиенту не отдаются стеки; 5xx пишутся в `error_logs` (без query/body, чтобы не сохранять ПДн) |
| Заголовки | Helmet в API; `nosniff`, `Referrer-Policy`, `Permissions-Policy` в web; `x-powered-by` отключён |
| Секреты | Только через переменные окружения; `.env` в `.gitignore`; в репозитории лишь `.env.example`. Демо-пароль существует только в seed, который не работает при `NODE_ENV=production` |
| Целостность записи | Транзакция с `FOR UPDATE` + exclusion constraint + уникальный idempotency key |

## Персональные данные

- **Минимизация**: клиент сообщает только имя и телефон (для связи по записи); аккаунт и пароль клиенту не нужны. Барбер видит только своих клиентов. Логи не содержат тел запросов.
- **Согласие**: обязательный чекбокс при записи (`customers.consent_at`).
- **На устройстве клиента** хранятся только токены его записей и последние имя/телефон для автозаполнения (`localStorage`); их можно убрать кнопкой «Убрать с этого устройства».
- **Экспорт**: `GET /businesses/:id/customers/:cid/export` (владелец, по запросу клиента), `GET /me/export` (сотрудник).
- **Удаление**: `DELETE /businesses/:id/customers/:cid` — обезличивание клиента; `DELETE /me` — удаление аккаунта сотрудника. История визитов остаётся без ПДн.
- Демо-данные полностью вымышлены (номера `+99890000000X`, `+9989100000XX`).

## Резервное копирование

`scripts/backup-db.sh` — `pg_dump -Fc` с ротацией 14 копий (проверено: дамп читается `pg_restore`). В production: запуск по расписанию, шифрование, хранение вне сервера БД, регулярная проверка восстановления.

## Исправленные уязвимости

| Дата | Что | Исправление |
| --- | --- | --- |
| 2026-11-19 | **High.** Владелец бизнеса A мог выдать временный пароль сотруднику, который одновременно владелец бизнеса B или администратор платформы, и войти в его аккаунт (межтенантный захват) | Сброс только для аккаунтов, целиком принадлежащих бизнесу; временный пароль на сервере позволяет только сменить его. Регрессионные тесты в `apps/api/test/platform.test.ts` |
| 2026-11-19 | **Medium.** Барбер мог открыть карточку чужого клиента своего барбершопа (заметки, история визитов у других мастеров) через «создать клиента» по телефону, ручную запись с чужим `customerId` или запись-и-отмену | Отменённые записи не дают доступа, чужой `customerId` отклоняется, создание по существующему телефону возвращает 409 без данных, барбер видит только свои визиты |

## Известные ограничения

- Телефоны не подтверждаются: возможны ложные записи на чужой номер (сдерживаются лимитами, барбер может позвонить клиенту) и регистрация на чужой номер (прав не даёт).
- Тот, у кого есть секретная ссылка на запись, может её отменить или перенести — ссылку нельзя пересылать посторонним (это сказано клиенту в интерфейсе).
- Нет Row Level Security в PostgreSQL (изоляция — на уровне приложения).
- Нет 2FA для PLATFORM_ADMIN и ограничения входа в админку по IP.
- Rate limit хранится в памяти процесса — при нескольких инстансах API нужен общий storage (Redis).
- Нет антибот-защиты (captcha) на гостевой записи и регистрации.
- CSP не настроена (Next.js inline-скрипты требуют nonce-конфигурации).
- Внешний аудит безопасности / пентест не проводился.
